# lifeping — v1 Specification

## 1. Overview

lifeping is a tiny self-hosted website that tells friends and family whether its owner is alive. The owner sends a manual "ping" (from a PC keybind or a phone shortcut), the server records the timestamp, and a public web page shows how long ago the last ping was, colour-coded by freshness, plus a short history of recent pings.

The whole thing is one Rust binary serving an embedded single-page UI, shipped as one Docker container behind Traefik.

### 1.1 Goals

The page must be public, need no login, and be instantly understandable by non-technical family members in French or English. Sending a ping must be a single action (one keypress on PC, one tap on phone). The deployment must be one container with one volume, configured entirely through environment variables. The codebase should stay small and boring.

### 1.2 Non-goals for v1

Notifications of any kind (ntfy, email, reminders, "back alive" messages), multiple users, ping metadata, a database, rate limiting (delegated to Traefik if ever needed), and any authentication for viewing the page. Section 11 documents the planned notification design so v1 does not paint itself into a corner.

## 2. Tech stack

| Concern | Choice |
|---|---|
| Language | Rust, edition 2024, stable toolchain |
| HTTP framework | `axum` on `tokio` |
| Serialization | `serde` + `serde_json` |
| Time handling | `time` crate (features: `formatting`, `parsing`, `macros`, `serde`) using RFC 3339 |
| Duration parsing | `humantime` (for values like `12h`, `1d 6h`) |
| Token comparison | `subtle` (constant-time equality) |
| Logging | `tracing` + `tracing-subscriber` (env-filter via `RUST_LOG`) |
| Frontend | Plain HTML + CSS + vanilla JS, no build step, no external resources |
| Container | Multi-stage Docker build producing a static musl binary |
| Dev/test deps | `tempfile`, `tower` (`ServiceExt::oneshot`), `http-body-util` |

Avoid adding further dependencies without a clear reason. No `clap`; argument handling is trivial (see 3.1).

## 3. Architecture

### 3.1 Binary

A single binary named `lifeping` with two modes selected by the first CLI argument. With no argument or `serve`, it runs the HTTP server. With `healthcheck`, it performs `GET http://127.0.0.1:<port>/healthz` against the configured bind port, exits 0 on HTTP 200 and 1 otherwise. The healthcheck mode exists because the runtime image has no `curl`; implement it with a plain `std::net::TcpStream` and a hand-written HTTP/1.1 request rather than pulling in an HTTP client crate.

### 3.2 Repository layout

```
lifeping/
├── Cargo.toml
├── src/
│   ├── main.rs        # arg dispatch, tracing init, server startup, graceful shutdown
│   ├── lib.rs         # pub fn build_app(state) -> Router, re-exports for tests
│   ├── config.rs      # env var parsing + validation
│   ├── store.rs       # ping log: load, append, query
│   ├── status.rs      # pure status computation (green/yellow/red/unknown)
│   ├── api.rs         # /api/* handlers
│   └── assets.rs      # embedded frontend files + handlers
├── web/
│   ├── index.html
│   ├── app.js
│   ├── style.css
│   └── fonts/
│       ├── lifeping-title.woff2
│       └── OFL.txt
├── tests/
│   └── api.rs         # integration tests against build_app()
├── scripts/
│   └── lifeping-ping  # client script for the PC keybind
├── Dockerfile
├── .dockerignore
├── compose.yaml
└── README.md
```

### 3.3 Shared state

Application state is an `Arc<AppState>` holding the parsed `Config` and a `Store`. The `Store` holds an in-memory `Vec<OffsetDateTime>` (sorted ascending, oldest first) behind a `tokio::sync::Mutex`, plus the path of the log file. The mutex also serializes file appends, which is sufficient because this process is the only writer.

### 3.4 Graceful shutdown

The server must shut down cleanly on SIGTERM and SIGINT (use `axum::serve(...).with_graceful_shutdown(...)` with `tokio::signal`), so `docker stop` does not wait for the kill timeout.

## 4. Storage

### 4.1 Format

A plain text file at `${LIFEPING_DATA_DIR}/pings.log`. One ping per line, each line an RFC 3339 UTC timestamp with second precision and a `Z` suffix, terminated by `\n`:

```
2026-09-26T08:12:44Z
2026-09-26T19:03:10Z
2026-09-27T07:58:02Z
```

Timestamps are always generated by the server clock at the moment of the request. Clients never supply a timestamp.

### 4.2 Startup

If the data directory does not exist, create it. If the file does not exist, treat the history as empty (the file is created on first append). Otherwise read it line by line: trim whitespace, skip empty lines, parse each line as RFC 3339. A line that fails to parse is logged at `warn` with its line number and skipped; it must not crash the server and the file must never be rewritten or "repaired" automatically. After loading, sort ascending. Log the number of pings loaded at `info`.

### 4.3 Append

Under the store mutex: take `OffsetDateTime::now_utc()` truncated to whole seconds, open the file with `append(true).create(true)`, write the formatted line, call `sync_data()`, then push onto the in-memory vector. Only after the write succeeds does the handler return success. If the write fails, return 500 and do not modify the in-memory vector.

### 4.4 Retention

All pings are retained forever. Size is not a concern (hourly pings for ten years is roughly 87,600 lines, about 1.8 MB).

## 5. Configuration

All configuration comes from environment variables. Invalid configuration must fail fast at startup with a clear error message naming the variable.

| Variable | Required | Default | Description |
|---|---|---|---|
| `LIFEPING_TOKEN` | one of these two | none | Bearer token for `POST /api/ping` |
| `LIFEPING_TOKEN_FILE` | one of these two | none | Path to a file containing the token (trailing whitespace trimmed); for Docker secrets |
| `LIFEPING_YELLOW_AFTER` | no | `12h` | Age after which status becomes yellow (humantime format) |
| `LIFEPING_RED_AFTER` | no | `24h` | Age after which status becomes red (humantime format) |
| `LIFEPING_HISTORY` | no | `10` | Number of most recent pings returned for the UI, 1 to 1000 |
| `LIFEPING_DATA_DIR` | no | `/data` | Directory containing `pings.log` |
| `LIFEPING_BIND` | no | `0.0.0.0:8080` | Listen address |
| `RUST_LOG` | no | `lifeping=info` | Log filter |

Validation rules: exactly one of `LIFEPING_TOKEN` / `LIFEPING_TOKEN_FILE` must be set and the resulting token must be non-empty; log a `warn` (not an error) if it is shorter than 32 characters. `LIFEPING_RED_AFTER` must be strictly greater than `LIFEPING_YELLOW_AFTER`, and both must be greater than zero. The token must never be logged.

## 6. Status logic

Implemented as a pure function in `status.rs` so it is trivially unit-testable:

```rust
pub enum Status { Unknown, Green, Yellow, Red }

pub fn compute(latest: Option<OffsetDateTime>, now: OffsetDateTime,
               yellow_after: Duration, red_after: Duration) -> Status
```

With no ping at all, the status is `Unknown`. Otherwise let `age = now - latest`: if `age < yellow_after` it is `Green`, else if `age < red_after` it is `Yellow`, else `Red`. Boundaries are inclusive on the worse side (an age of exactly `yellow_after` is yellow). A negative age (latest ping in the future due to a clock change) is treated as `Green`.

The frontend implements the same rules in JavaScript from the thresholds the API provides (see 8.4); the server-computed status in the API is for `curl` users and tests.

## 7. HTTP API

All JSON responses use `Content-Type: application/json`. All `/api/*` responses carry `Cache-Control: no-store`.

### 7.1 `GET /api/status`

Public. Returns the current state.

```json
{
  "now": "2026-09-27T09:30:00Z",
  "status": "green",
  "latest": "2026-09-27T07:58:02Z",
  "history": [
    "2026-09-27T07:58:02Z",
    "2026-09-26T19:03:10Z",
    "2026-09-26T08:12:44Z"
  ],
  "total_pings": 3,
  "thresholds": {
    "yellow_after_secs": 43200,
    "red_after_secs": 86400
  }
}
```

`now` is the server's current time, used by the client to correct for clock skew. `status` is one of `unknown`, `green`, `yellow`, `red`. `latest` is `null` when there are no pings. `history` is newest first, contains at most `LIFEPING_HISTORY` entries, and includes the latest ping as its first element. `total_pings` is the full count on disk.

### 7.2 `POST /api/ping`

Requires `Authorization: Bearer <token>`. The request body is ignored (clients may send none). Compare the presented token to the configured one with `subtle::ConstantTimeEq`.

On success, return `200 OK` with the recorded timestamp so client scripts can show it:

```json
{ "timestamp": "2026-09-27T09:30:00Z" }
```

A missing, malformed, or wrong `Authorization` header returns `401 Unauthorized` with header `WWW-Authenticate: Bearer` and body `{"error":"unauthorized"}`. A storage failure returns `500` with `{"error":"storage failure"}` and logs the underlying error. Log each successful ping at `info` (timestamp only). Log failed auth at `warn` without echoing the presented token.

### 7.3 `GET /healthz`

Returns `200 OK` with body `ok`. No auth, no dependency checks.

### 7.4 Static assets

`GET /` serves `index.html`, `GET /app.js` serves the script, `GET /style.css` serves the stylesheet. `GET /fonts/lifeping-title.woff2` serves the title font (`font/woff2`). All are embedded at compile time with `include_str!`/`include_bytes!` from `web/`. Serve them with correct `Content-Type` (including `charset=utf-8`) and `Cache-Control: no-cache`. Any other path returns 404.

### 7.5 Security headers

Apply to every response:

```
Content-Security-Policy: default-src 'none'; script-src 'self'; style-src 'self'; img-src 'self' data:; font-src 'self'; connect-src 'self'; base-uri 'none'; form-action 'none'; frame-ancestors 'none'
X-Content-Type-Options: nosniff
Referrer-Policy: no-referrer
```

This is why JS and CSS are separate files rather than inline. HSTS is left to Traefik.

## 8. Frontend

### 8.1 Principles

Plain HTML, CSS, and vanilla JS with no framework, no build step, and no external requests of any kind (no CDN, no web fonts, no analytics). It must work well on phones first, since family will mostly open it there. Use the system font stack.

### 8.2 Layout

The page has two parts. At the top, a large status card dominates the viewport: a coloured indicator with an icon, a short headline, and a secondary line giving the relative age ("last seen 3 hours ago") with the exact local date and time in smaller text below. Beneath it, a "Recent pings" section lists the history entries newest first, each showing the local date/time and its relative age. A small FR | EN language toggle sits in the top-right corner. A discreet footer line shows when the page last successfully refreshed.

There is no name, photo, or personal text on the page.

### 8.3 Visual states

| Status | Colour | Icon idea |
|---|---|---|
| unknown | grey | question mark |
| green | green | check / heartbeat |
| yellow | amber | clock |
| red | red | exclamation |

Colour must never be the only signal: each state has its own headline text and icon. Support `prefers-color-scheme: dark` with adjusted tokens, keep contrast accessible in both modes, and respect `prefers-reduced-motion` if any animation (e.g. a gentle pulse on green) is added. The status region has `aria-live="polite"` so screen readers announce state changes.

Update `document.title` to reflect the state (e.g. `🟢 lifeping`, `🟡 lifeping`, `🔴 lifeping`, `⚪ lifeping`), and update the favicon to a coloured circle using an inline SVG data URL (allowed by the CSP `img-src data:`).

### 8.4 Refresh behaviour

On load, fetch `/api/status`, then poll every 30 seconds. Pause polling while `document.hidden` is true and fetch immediately when the page becomes visible again.

On each successful response, compute `offset = Date.parse(now) - Date.now()` and store it. Every 10 seconds, re-render relative times and recompute the status locally from `latest`, the thresholds, and `Date.now() + offset`, using the same rules as section 6. This makes the card flip from green to yellow on time even between polls and even if the viewer's device clock is wrong.

If a fetch fails, keep displaying the last known data and show a non-alarming notice ("Can't reach the server, retrying…" / "Serveur injoignable, nouvel essai…") until the next success. The notice must be visually distinct from the red "no sign of life" state so a network blip is never mistaken for bad news.

### 8.5 Internationalisation

Supported languages are French and English. On first visit, walk `navigator.languages` and pick the first entry whose primary subtag is `fr` or `en`; default to `en`. The toggle switches instantly without reloading, persists the choice in `localStorage` (wrapped in `try/catch`, falling back gracefully if storage is unavailable), and sets `<html lang>`.

Relative times use `Intl.RelativeTimeFormat` with `numeric: "auto"` in the active language, choosing the largest sensible unit (seconds under a minute, minutes under an hour, hours under two days, days beyond). Absolute times use `Intl.DateTimeFormat` with `dateStyle: "medium"` and `timeStyle: "short"` in the viewer's local timezone.

All UI strings live in one dictionary object in `app.js`. Threshold hours in messages are derived from the API thresholds, not hard-coded. Initial strings:

| Key | English | French |
|---|---|---|
| `headline.green` | Alive and well | En vie et en forme |
| `headline.yellow` | Probably fine, quiet for a while | Sûrement rien de grave, pas de nouvelles depuis un moment |
| `headline.red` | No sign of life for over {hours} hours | Aucun signe de vie depuis plus de {hours} heures |
| `headline.unknown` | No ping yet | Aucun ping pour l'instant |
| `lastSeen` | Last seen {relative} | Vu pour la dernière fois {relative} |
| `history.title` | Recent pings | Pings récents |
| `history.empty` | Nothing here yet | Rien pour l'instant |
| `footer.updated` | Updated {relative} | Mis à jour {relative} |
| `error.unreachable` | Can't reach the server, retrying… | Serveur injoignable, nouvel essai… |

`{relative}` receives the output of `Intl.RelativeTimeFormat` (e.g. "3 hours ago" / "il y a 3 heures").

## 9. Deployment

### 9.1 Dockerfile

A multi-stage build. The builder stage uses `rust:1-alpine` (which produces a statically linked musl binary natively), installs `musl-dev`, caches dependencies by building against a stub `main.rs` before copying the real sources, and builds with `--release --locked`. The runtime stage uses `gcr.io/distroless/static-debian12:nonroot`, copies only the binary, declares `VOLUME /data`, exposes 8080, and sets:

```dockerfile
HEALTHCHECK --interval=30s --timeout=3s --start-period=5s --retries=3 \
  CMD ["/usr/local/bin/lifeping", "healthcheck"]
ENTRYPOINT ["/usr/local/bin/lifeping"]
CMD ["serve"]
```

The container runs as the distroless `nonroot` user (UID/GID 65532). The README must note that a bind-mounted data directory needs to be writable by that UID (`chown 65532:65532`), while a named volume works out of the box.

Enable `lto = true`, `codegen-units = 1`, `strip = true`, and `panic = "abort"` in the release profile.

### 9.2 compose.yaml

Provide a compose file with placeholders clearly marked for the router host, entrypoint name, cert resolver name, and external network name:

```yaml
services:
  lifeping:
    build: .
    image: lifeping:latest
    container_name: lifeping
    restart: unless-stopped
    environment:
      LIFEPING_TOKEN_FILE: /run/secrets/lifeping_token
      LIFEPING_YELLOW_AFTER: 12h
      LIFEPING_RED_AFTER: 24h
      LIFEPING_HISTORY: "10"
    secrets:
      - lifeping_token
    volumes:
      - lifeping-data:/data
    networks:
      - proxy
    labels:
      - traefik.enable=true
      - traefik.http.routers.lifeping.rule=Host(`lifeping.example.com`)   # CHANGE ME
      - traefik.http.routers.lifeping.entrypoints=websecure                # CHANGE ME
      - traefik.http.routers.lifeping.tls.certresolver=letsencrypt         # CHANGE ME
      - traefik.http.services.lifeping.loadbalancer.server.port=8080

secrets:
  lifeping_token:
    file: ./secrets/lifeping_token

volumes:
  lifeping-data:

networks:
  proxy:
    external: true   # CHANGE ME to your Traefik network name
```

The README should show how to generate a token, e.g. `openssl rand -hex 32 > secrets/lifeping_token`, and remind the user to keep `secrets/` out of git (include it in `.gitignore`).

## 10. Clients

### 10.1 PC script (`scripts/lifeping-ping`)

A bash script using long-form flags wherever a long form exists. It reads the endpoint from `LIFEPING_URL` (default placeholder `https://lifeping.example.com`) and the token from `${XDG_CONFIG_HOME:-$HOME/.config}/lifeping/token`, sends the ping, and reports the result with a desktop notification.

```bash
#!/usr/bin/env bash
set -o errexit -o nounset -o pipefail

readonly url="${LIFEPING_URL:-https://lifeping.example.com}"
readonly token_file="${XDG_CONFIG_HOME:-$HOME/.config}/lifeping/token"

if [[ ! -r "$token_file" ]]; then
  notify-send --urgency=critical --app-name=lifeping "lifeping" "Token file not found: $token_file"
  exit 1
fi

if response="$(curl --silent --show-error --fail --max-time 10 \
      --request POST \
      --header "Authorization: Bearer $(<"$token_file")" \
      "$url/api/ping" 2>&1)"; then
  notify-send --app-name=lifeping "lifeping" "Ping sent: $response"
else
  notify-send --urgency=critical --app-name=lifeping "lifeping" "Ping failed: $response"
  exit 1
fi
```

Claude Code may refine the success message (e.g. parse the timestamp out of the JSON with a small `sed` expression, avoiding a `jq` dependency). The token must not appear in the process list longer than necessary; reading it inline as above is acceptable for a personal machine.

The README documents installation to `~/.local/bin/lifeping-ping` and a Hyprland keybind:

```
bind = SUPER, P, exec, ~/.local/bin/lifeping-ping
```

### 10.2 Phone (GrapheneOS, HTTP Shortcuts app)

The README documents creating a "Regular HTTP Shortcut" in the open-source HTTP Shortcuts app: method `POST`, URL `https://lifeping.example.com/api/ping`, header `Authorization: Bearer <token>`, response handling set to show a toast on success and on failure, then adding it to the home screen as a one-tap shortcut or widget.

## 11. Future work (out of scope for v1, design must not block it)

Notifications will be added later via ntfy once an instance exists. The intended design is recorded here so v1's structure accommodates it (in practice: keep status computation pure and reusable, and keep the store's API free of HTTP concerns).

A background task will wake every minute and evaluate the status. Reminders to the owner will fire at configured times of day in a configured timezone (e.g. `LIFEPING_REMINDER_TIMES=09:00,13:00,19:00`, `LIFEPING_TZ=Europe/Paris`), only while the status is yellow, repeating at each scheduled time, so no reminders arrive at night. When the status turns red (24h), a one-off alert goes to a separate family topic. When a ping arrives after a family alert was sent, a "back alive" message goes to the family topic. Which alerts have been sent for the current stale episode will be persisted in a small state file in the data directory, so a container restart does not re-send them.

Other possible later additions: ping metadata (at which point the log migrates from plain lines to JSON Lines, with the loader accepting both formats during the transition) and automatic pings triggered by events such as PC startup.

## 12. Testing

Unit tests cover `status::compute` (no ping, each state, exact boundary values, future timestamp), config validation (missing token, both token vars set, red ≤ yellow, bad durations, history out of range), and store loading (empty/missing file, valid lines, malformed lines skipped, unsorted input sorted).

Integration tests in `tests/api.rs` build the router with `build_app()` over a `tempfile` data directory and drive it with `tower::ServiceExt::oneshot`. They must verify: `GET /api/status` on an empty store returns `unknown` with `latest: null`; `POST /api/ping` without a header, with a wrong token, and with a non-Bearer scheme each return 401 with `WWW-Authenticate`; a valid ping returns 200 with a timestamp and subsequent status is `green` with that timestamp as `latest`; history is newest first and truncated to the configured length while `total_pings` reflects everything; pings survive re-creating the app from the same data directory; static routes return the right content types; unknown paths return 404; and the security headers are present.

`cargo clippy --all-targets -- --deny warnings` and `cargo fmt --check` must pass.

## 13. Acceptance criteria

| # | Criterion |
|---|---|
| 1 | `docker compose up --build` starts a healthy container with a token secret and no other setup |
| 2 | Opening the page in a browser set to French shows French; otherwise English; the toggle switches instantly and persists |
| 3 | With no pings, the page shows the grey "no ping yet" state |
| 4 | Running `lifeping-ping` produces a success notification and the page turns green within 30 seconds without a manual reload |
| 5 | With thresholds temporarily set to `1m`/`2m`, an open page turns yellow then red on time without any new ping |
| 6 | The history shows at most `LIFEPING_HISTORY` entries, newest first, in the viewer's local time |
| 7 | Restarting the container preserves all pings |
| 8 | A wrong token is rejected with 401 and is not written to the log |
| 9 | Stopping the server makes the page show the "can't reach server" notice, clearly distinct from the red state |
| 10 | The page loads no resources from any other origin and works on a narrow phone screen in light and dark mode |
| 11 | All tests, clippy, and fmt checks pass |
